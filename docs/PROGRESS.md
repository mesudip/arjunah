# Project progress

## 2026-10-03 — release audit fixes for 1.0.0-beta.2

1.0.0-beta.2 was bumped but never tagged or published. It ships with this audit and the 2026-10-02/03 settings and desktop work below, still as beta.2; no version string changed.

- **Consent sheet (SPEC 4).** `enable()` needs no gesture, and the sheet used to focus Allow, so one key the visitor meant for the page could grant level 2. The sheet now focuses itself, keeps Tab inside it, ignores untrusted clicks, and arms Allow (`aria-disabled` until then) only after `CONSENT_ARM_MS` (1 s) on screen without a break in a visible, focused tab; in Chrome an IntersectionObserver v2 watch on the card also disarms it while it is covered or the page makes the host transparent. Site-written text (reason, names, descriptions, labels, model and group names, discovered tools) goes through `ArjunahHosted.plainLine`: no direction overrides or invisible characters, no line breaks; the system prompt keeps its breaks through `plainText`. Browser tests answer consent with `tests/helpers/consent.mjs` (`approveConsent`/`denyConsent`, Shift+Tab to the last or second-last button) and the Firefox equivalents in `tests/helpers/firefox.mjs`.
- **`require` in hosted chat (SPEC 4).** The check moved into `resolveSiteConfig`, so hosted chat is held to it as page rounds are; a `require: { local: true }` site whose Ollama model went away no longer falls back to a cloud default.
- **Loop prompts and tools (SPEC 15.1).** `loop.inputs: true` is now declared to use `input.client`; without it the extension cancels the request and shows no prompt. Consent says a loop can ask for approvals, and for values when declared; prompts name the asking origin, and a site-written tool name containing the extension's name is dropped. A loop with site tools requests `tools.site`, and `loop.tool` refuses without it. A loop's consent always carries the card disclosure. SDK `AISiteLoop.inputs`.
- **Remote-input hint.** The prompt for a declared remote tool's input now says the current page can see what is typed; SECURITY.md documents that keyboard, input, and paste events leave the closed shadow root.
- **Provider state (SPEC 5.4).** One-off completions share `document:<session>`; a final round now deletes only its own turn's entries (`providerState.forget`) and storing prunes nothing there, so parallel loops in one document keep each other's signatures.
- **Clearing stored state (SPEC 11.2).** The install key rotates first, then direct turns and desktop-backed hosted turns end, then entries and threads go, so a round starting during the clear is refused instead of verifying the old key. Hosted chat desktop threads are now derived (`desktopThreadId` over `hosted:<panel id>`) and recorded with their origin, so revocation and clearing end them and a cleared panel never resumes the old session.
- **Desktop thread queue (SPEC 12.3.1).** Turns on one `threadId` run one at a time (`desktop/lib/server.mjs` lanes): a turn waits until the previous session has ended and its process has exited, a closed waiting request leaves without starting the agent, a wait past 140 s is `TIMEOUT`, and ending a thread stops its run before deleting the scratch directory. `SessionRegistry.create` now calls the caller's `onEnd`.
- **Resumed threads send only what is new.** A thread's `seen` was the turn's starting length plus one, so the tool rounds in between were never counted and the next turn replayed the old tool result and answer as "the conversation continued". Tool-result requests now advance the session's `conversationLength`, so the next turn's continuation is only the new message.
- **Agent-run limit (desktop only, not in the SPEC).** `SESSION_LIMITS.maxSessions` (6, since alpha.1, undocumented until now) used to kill the oldest run for a newcomer, working or not, and `end()` never answered the request waiting on it, which then sat out the 170 s event timeout while holding its conversation's lane. Now `SessionRegistry.makeRoom()` evicts only the run paused on the browser the longest (its late tool results start a fresh run from the transcript, as SPEC 12.3.1 already requires); with all six working, the turn is refused at once with 429 `RATE_LIMITED`, `reason: "busy"`, `retryAfterMs: 5000`, which the extension shows in its own sentence rather than the subscription rate-limit one. `end(kill, reason)` answers any waiter immediately, and `emit` delivers a final answer before ending. DESKTOP.md describes the per-chat queue and the limit.
- **Ollama 403.** Only an empty-bodied 403 (Ollama's own Origin/Host check) gets the `OLLAMA_ORIGINS` sentence; a 403 with a body is `OLLAMA_PROXY_REFUSAL`, or `OLLAMA_KEY_REFUSAL` (`NOT_CONFIGURED`) when a key is set. The e2e mock now answers like Ollama, with no body.
- **Widget (`arjunah-widget`).** SSE framing follows EventSource (CRLF, CR, LF, split CR|LF, BOM, comments, multi-line data) through the new exported `createEventStreamParser`; Stop cancels the running turn's own thread; `eventStreamResponse` calls the generator's `return()` once on every early end; `BridgeAccessRequest` matches `enable()` (level, capabilities, context, reason, require, composer), and a refused `enable()` is shown to the visitor and reported to `onError`.
- **Settings and release.** "Skip to content" focuses the current view instead of routing to Overview. `scripts/check.mjs` now fails when README's Status line or CONFORMANCE's "Last updated … for" names another version. The publish workflow's registry check waits up to 45 minutes per package (npm took 39 for beta.1).
- **Verification.** `npm run check` passes with 357 unit tests (new: a resumed thread's prompt after a tool turn is only the new message, a seventh run refused at once with nothing killed, the newest paused run evicted rather than the oldest working one and its late results answered by a fresh run, an ended session answering its waiter at once, the busy refusal's own wording; hosted-chat `require`, side-by-side one-off loops, the clear race held at its first storage read, hosted threads ended by clear and revoke, loop `inputs` validation and consent lines, `plainLine`/`plainText`, Ollama 403 variants, four desktop thread-queue tests in `tests/desktop-threads.test.mjs`, nine widget stream tests in `tests/widget-stream.test.mjs`); the new tests were each checked to fail without their fix. Browser suites pass: `lint:firefox` (0 warnings), Chrome, Chrome security (new: stray Enter/Space and a transparent sheet cannot approve, Allow re-arms after the sheet is shown again), hosted surfaces and loop, widget, desktop, polling, the Ollama mock, and Firefox with its hosted loop.
- **Open.** Not checked in the user's Brave session or against live providers. Still open from the audit, not fixed here: a site model grouped under a provider-like site name can pass as the visitor's own; the extension ID is visible to pages through web-accessible resources. npm `latest` still points at `1.0.0-alpha.1`.

## 2026-10-03 — desktop provider reads answer at once; discovery reports its own timings

- **Why.** The settings page sat on the Desktop app view for 20+ seconds on every load, sometimes ending in "Desktop app request was cancelled or timed out". Every ordinary `GET /api/providers` ran the light pass before answering (each signed-in CLI probed for models and plan usage, `opencode models` alone allowed 60 s, a full detection whenever one adapter could not confirm itself), and the extension waited up to 30 s for it. The 20 s matches the default 20 s command deadline, which is what the Claude Code row reported when the companion's own run of `claude auth status` hung; that case was not reproduced from a terminal.
- **Companion.** An ordinary read is answered from the view the companion already has; a view older than `providerStaleMs` (30 s) starts one light pass behind it, and a pass that changes anything is published, so a connected browser reads again. A first read, a settings change, and `?refresh=1` still wait for fresh results. Every discovery command (`run()` and the JSON control probes) logs its duration and outcome at debug level under `discovery`, and each pass logs its total and how many providers are available.
- **Extension.** `desktop.status { cached: true }` returns the stored link and the last reachability check without contacting the companion; the settings page draws it at once, marked as checking (spinner on the desktop icon, last-known subscriptions dimmed with "Updating…", a busy Check again), and an explicit re-check says it can take up to a minute. A desktop read that takes 1 s or more is logged with its split (`status`, `providers`, `sync`).
- **Verification.** `npm run check` passes with 334 unit tests (new: an ordinary read answers from the cached view while a slow light pass runs, starts only one pass, and the next read sees its result). ## 2026-10-02 — round streaming on the page API (SPEC 5.3, 5.4, 10)

- **API.** `session.models.stream(request, { signal })` and `conversation.stream(request, { signal })` return an async iterable of `{ type: "output.delta", text }`, `{ type: "reasoning.delta", text }`, `{ type: "stalled" }`, and last `{ type: "result", result }`. The result is the response of the same background path as `models.generate` (`directGenerate`: validation, `require`, `stripRaw`, traits, `providerState`, usage, `_warnings` logged and removed by the page API), so it equals a generate of the same request. Errors reject `next()` with the section 9 error (details with `requestId`/`retryable` come from the content script's `respond` as for generate). Aborting the signal posts the existing `cancel` and rejects `ABORTED`; `return()` (a `break`) posts the same `cancel` and ends the iteration without an error. Tool calls are only in the result.

## 2026-10-01 — Ollama: self-hosted servers and Ollama Cloud

- **Two providers, one native wire format.** `ollama` is a server the user runs (any address they type; optional key for an authenticating proxy) and `ollama-cloud` is `https://ollama.com` with an API key. Streams are NDJSON (`message.thinking`, then `message.content`, usage on the `done` line); a stream that ends without `done` is an error, not a partial answer.
- **Capabilities come from the server, not from names.** Discovery reads `/api/tags`, then `/api/show` per model (four at a time, skipped when the digest is unchanged). `/api/show` is authoritative: on the test server `/api/tags` under-reported `gemma4:e2b` (no vision) and `qwen3.8:4b-distill` (no tools). ## 2026-09-30 — streamed thinking merged into chunks; stream memory bounded per event

- **A long answer no longer fails at 2 MB.** Every streamed token carries its own JSON envelope, so a reasoning model's wire size passed the 2,000,000-byte response cap long before its text did. Streams now have no total cap. What is held is bounded instead: the SSE parser keeps one event at a time and refuses one over `providerEventBytes` (8,000,000), which also stops a line that never ends. Answer and reasoning text keep their existing limits.
- **Streamed tool arguments stop growing at the limit.** Chat Completions, Anthropic and Responses concatenated argument deltas without bound until the stream ended, then `repairToolCalls` rejected anything over 64 KiB. The parsers now keep one character past the limit, which is enough for the repair to report the call as oversized, and names stop at 256 characters.
- **Anthropic arguments that do not parse are no longer run as `{}`.** A truncated or malformed `input_json_delta` string became `input: null`, which `anthropicResult` turned into `"{}"`, so the tool ran with no arguments. The raw text now goes through, and the tool loop tells the model its arguments were invalid.
- **Gemini no longer keeps every streamed part.** `streamedGemini` pushed each part object, envelope fields included, into an array for the whole round. Text and thoughts are folded into bounded strings as they arrive; only function-call parts are kept whole, since their args and thought signatures go back to Gemini unchanged.
- **Thinking crosses to the widget in batches.** Every reasoning token used to be its own `chrome.tabs.sendMessage` with a full activity envelope. `src/lib/reasoning.js` merges a round's reasoning deltas for at most 250 ms or 4,000 characters. Any other progress item sends the pending text first, so order is kept, and the round's `finally` sends whatever is left.
- **The renderer draws thinking in chunks of at most 50 words.** It used to rebuild the whole `pre.textContent` on every delta, copying everything drawn so far each time. `reasoningChunks` (exported from the renderer) splits incoming text at word boundaries. A word split across two deltas is counted once and never cut at a chunk boundary, and each chunk is one text node that later deltas extend with `appendData`. At most 60,000 characters stay on screen per turn: the oldest chunks go first, and the summary says the earlier text was trimmed. This applies to both the extension and the standalone widget.
- **Verification.** `npm run check` passes: 191 unit/security tests, five new (per-event cap, capped arguments reported as oversized, Anthropic pass-through, batch timing/order/size, 50-word chunking token by token, Gemini folding). All browser suites pass: Chrome, Firefox, Chrome security, hosted surfaces, desktop, idle polling, and zero-warning Firefox lint.
