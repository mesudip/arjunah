## 2026-09-20 — run phases in the widget, diagnostic logs in settings and the dashboard

- **The symptom.** A Codex turn showed “Asking GPT-5.6-Sol… 26.2s” and nothing else. The wait is real work — a version check, a login check, an account probe, a sandbox profile, the CLI launch, and an MCP startup — but none of it was reported, so a slow start was indistinguishable from a hang.
- **Phases (SPEC 12.3.1, 14.3).** Progress items gained `{ type: "phase", text }`, which the renderer shows as the live turn label. The companion emits one before provider detection (with how long detection took in the log), before launch, and on resume; each adapter emits one when it prepares its workspace, bridges tools, and launches; and the CLI's own lifecycle events become phases: Codex `thread.started`, `turn.started`, `item.started` (reasoning, message, tool call, web search) and `turn.completed`, Claude Code's `system/init`, `user` and `result`, and OpenCode's first streamed event.
- **A delta bug the phases exposed.** `pushProgress` merged adjacent text into the last item even after the browser had polled it, so anything appended after a poll was never delivered. Items are now merged only while still uncollected; the route records how far the browser has read.
- **Diagnostics (SPEC 12.3.2).** The companion keeps a bounded log (`desktop/lib/logs.mjs`) served at `GET /api/logs`, and the extension keeps its own (`src/lib/logs.js`, mirrored to session storage so a service-worker restart does not lose it). Extension settings gained a Diagnostics card with both, a live refresh, copy, and clear; the desktop dashboard shows its own beside the activity list. Adapters now report the CLI's stderr and exit status into the log, which is where a `codex login` problem or a failed MCP startup will surface.
- **What is not logged.** Prompts, model output, tool arguments and results, page context, keys, and pairing tokens. A logged command line keeps its flags and elides any value over 60 characters, which is what keeps `--system-prompt` out of it. Neither log leaves the machine and neither is part of sync.
- **Verification.** `npm run check` (142 unit tests, static checks, formatting). Widget E2E asserts a backend `agent.phase` becomes the live label; desktop E2E reads both logs through the real settings page in Chrome and asserts the prompt is absent from the companion's.

## 2026-09-20 — image input for Claude Code and Codex

- **The flag was honest, the plumbing was the limit.** Desktop providers reported `supportsVision: false` because the companion hands a CLI one text prompt on stdin, and `src/lib/desktop.js` flattened every image part to the string `[image]`. Both CLIs accept pictures; only this run path did not.
- **Claude Code.** A run with attachments switches to `--input-format stream-json` and writes one user message carrying the prompt plus base64 image blocks. Text-only runs keep the plain-text stdin path, so the well-tested route is unchanged. Verified live against `claude` 2.1.269: a 64×64 red PNG came back "Red", and the `result` event shape `parseClaudeOutput` reads is identical.
- **Codex.** `codex exec` takes images as files, so each attachment is written into the run's scratch directory and passed with `-i`. `-i` follows `resume` on a resumed thread because the subcommand parses it. Verified live against `codex-cli` 0.155.0-alpha.2.6. Per-model vision now comes from the catalog's `input_modalities` and from `model/list`'s image flag, both of which the adapter previously read and threw away.
- **OpenCode stays text only.** It was the one provider that leaked an unusable capability: `parseModelList` copied the upstream model's image flag, per-model capabilities win over the provider flag in `src/lib/catalog.js`, so an OpenCode vision model showed the attach button and the picture then became the literal text `[image]`. It is now pinned to `vision: false` with the reason in a comment, since `opencode run` has no image input to deliver one.
- **Wire.** A user message may carry `images: [{ mediaType, data }]`, at most four per message and eight per prompt, bounded in the browser and again in the companion, refused on non-user roles, and dropped for a provider without vision. The companion's body limit rose from 5 MB to 12 MB to match the extension's own `requestBytes`. SPEC 12.2 and 12.3 describe it; SECURITY.md carries the bounds as a property and OpenCode as the remaining limitation.
- **Verification.** `npm run check`: static checks, formatting, and 138 unit tests pass, including new coverage for the vision and no-vision companion paths, the attachment bounds, the newest-first prompt image collector, both adapters' delivery shapes, the OpenCode pin, and the extension forwarding images beside the flattened text.

The conformance list, `docs/CONFORMANCE.md`, and the two `hosted-1.2` test files (now `hosted-surfaces`) lost their era labels with it. Entries below this one keep the version numbers they were written under.
- **SPEC 8.2, model and effort picker.** The picker was extension chrome filling a renderer slot, which is why the standalone widget had none. It is now the renderer's: a host supplies section 5.2 entries and receives the choice, and a host that refuses a switch gets the previous selection back rather than a composer claiming a model that is not answering. `widget.models` and `widget.defaultModel` give a standalone site the same control, and each turn carries `model` and `reasoning`.
- **SPEC 8.3, entity mentions.** The composer moved from a `textarea` to a contenteditable element so a mention is one atomic chip a single backspace removes whole. `@` searches the host's entity source (a `search` function, or `GET entities?q=` on the backend), and the chip submits as a new section 5.3 `mention` content part. The id reaches the backend, which can resolve it from its own data; a provider only ever sees `@label`, enforced by `flattenMentions`.
- **SPEC 7.3 in standalone mode.** `userInputs` was native to the extension but its prompt lived in `content.js`, so section 14.1 promised the widget something it did not have. The prompt is now the renderer's and `invocation.requestInput(id)` works in both modes, with the 120-second timeout and the four-prompts-per-invocation cap enforced in the renderer.
- **SPEC 14.1 host callbacks.** `onTurnStart`, `onTurnEnd` (with usage), `onThreadChange`, `onModelChange` and `onError`, plus `openThread`, `newThread`, `getControls`, `setControls` and `setModels` on the mounted object. A throwing callback cannot end a turn.
- **One renderer, still.** `content.js` lost the model menu, the effort select, `showToolInput`, its `compactNumber` copy and roughly 200 lines with them; it now hands the renderer a catalog and answers whether a switch held. The published widget is still byte-identical to the file the extension loads, which `scripts/check.mjs` enforces.

## 2026-09-20 — v1.2.0: transcript cards, tool progress, site-owned threads, declared remote tools, and a standalone renderer

### Scope

- **SPEC 1.2.** New sections 7.4 (transcript cards), 7.5 (tool progress), 7.6 (site-owned threads), 7.7 (declared remote tools), 8.1 (renderer requirements) and 14 (standalone renderer), plus security boundaries 13–15, consent disclosure rules, and conformance items for each. The protocol version moved to 1.2.0 across the manifest, page API, SDK, desktop companion, and packages.
- **Renderer extraction.** The chat surface moved out of `src/content.js` into `src/renderer/core.js`, a dependency-free classic script the content script loads beside itself. It owns the panel, transcript, activity feed, cards, progress lines, thread panel, composer, attachments, and drag. The content script kept everything that is wallet-specific: consent, provider and model pickers, thinking effort, context sharing, usage and quota, the setup card, the launcher, and the bridge.
- **Cards.** A tool that declares `outputContent: ["text", "card"]` may return one bounded card (text, list, button, form) beside its text. The model receives only the text. A `message` action sends its exact declared text as a visible user bubble; a `local` action calls `onCardAction` and can return a replacement card, which the broker re-validates before the renderer draws it. No HTML, Markdown, links, or images.
- **Progress.** `invocation.reportProgress(text)` renders one ephemeral line under the running tool's step, capped at 200 characters and 50 reports per invocation, and never enters model messages, history, or a stored transcript.
- **Site-owned threads.** A manifest may declare `threads` callbacks (`list`, `create`, `load`, `append`, `rename?`, `delete`). The renderer drives them, the extension validates and bounds everything that comes back, and consent states that the site stores the conversation. Loaded messages reach the model between explicit untrusted markers, and the extension applies its own 40-message budget after any truncation the site performed. Without `threads`, history stays document memory exactly as before. `thread.end` releases only the desktop thread behind one conversation.
- **Declared remote tools.** An `mcpServers` entry may carry `tools`. The extension then skips `tools/list`, folds the definitions into the fingerprinted contract, uses single-stage consent, and passes `{ arjunah: { conversationId } }` in `params._meta` on `tools/call`.
- **Standalone widget.** New `arjunah-widget` package (SPEC 14): the extension's own renderer plus a bounded client for a site backend — SSE turn stream, thread routes, card actions, and page-run client tools. `scripts/build-widget.mjs` builds it from `src/renderer/core.js` and `src/lib/{cards,schema,errors,constants}.js`, and a static check fails if the published renderer drifts from the one the extension loads.

### Verification

- `npm run check`: static checks, SDK and widget builds, formatting, and 130 unit tests pass (12 new: card node set, bounds, form values, declared tool results, `outputContent` combinations, declared MCP tools, thread contracts, `_meta` routing, single-stage consent, changed-declaration re-consent, and untrusted-history markers).
- Chrome E2E, Firefox E2E (155.0.1), and the Chrome security suite pass unchanged after the renderer extraction, which is the regression evidence for that refactor.
- New `tests/e2e/hosted-1.2.mjs` (wallet mode, real extension, mock provider): a site tool returns a card and reports progress; the card renders inside the closed shadow root and its local action round-trips through the page bridge to `onCardAction`, is re-validated, and swaps in place with no further provider request; thread `list`, `create`, and `append` run through the bridge and the site stores all three entries of the turn; neither the card nor the progress text appears in any captured provider request.
- New `tests/e2e/widget.mjs` (no extension installed): the standalone package against a mock backend covers the event stream, a `tool.client` round executed in the page, a card with both action kinds, an in-place card update, a `progress` line, and thread switch/create/replay.
- The trip planner demo now ships a card-returning `review_trip` tool, progress reporting in the destination search, `onCardAction`, and a site-owned thread store.

### Limits and next work

- Thread titles come from the first user message; there is no model-generated title.
- Standalone mode provides none of the wallet guarantees, and the package README says so plainly. A ChatKit server adapter (translating that event stream into section 14) remains unimplemented.
- Neither new browser suite has run on Firefox; both use Chrome for Testing. The widget package has not been published to npm.

## 2026-09-20 — line-by-line review of the release diff

- Full suite re-run green after every change below: `npm run check` 118/118, Chrome/Firefox/security/desktop e2e, and `web-ext lint` at 0 errors/0 warnings.
- **Companion crash fixed.** `spawnAgent` wrote the prompt with `child.stdin.end(stdin)` and never listened for `error` on that stream, and nothing in `desktop/` installs an `uncaughtException` handler. A CLI that exits before draining stdin (an auth failure is the common case) therefore killed the whole companion once the prompt exceeded the pipe buffer. Reproduced at 200 KB, which ordinary transcripts reach (`LIMITS.internalMessageChars` is 180,000); the OpenCode stdin switch made it newly reachable for that adapter. Both spawn paths now attach `stdin.on("error")`, and `tests/desktop.test.mjs` covers it — the test fails with the listener removed.
- **Provider visibility unified.** `hostedSettings` and `brokerStatus` had each inlined a copy of the exposure rule that diverged from `exposedProviders()`: it applied no restriction below level 2, and dropped that helper's guarantee that the site's pinned provider stays listed, so a narrowed level-2 site could not see the model actually answering in its own switcher. The widget now calls `exposedProviders()` at level 2 and leaves levels 0/1 alone; consent is never filtered, because that dialog is how a grant gets widened and the page cannot read it.
- **Usage ledger.** Aggregating a turn into one request had moved `recordUsage` onto the success path only, so a turn that hit the tool-round limit, was cancelled, or failed on a later round recorded nothing despite having spent tokens. The round loop now settles in a `finally`, still counting one request per turn.
- **Sampling controls.** Rejecting `temperature`/`maxTokens` with `INVALID_REQUEST` broke conforming sites: SPEC section 5 documents both, and at level 1 a site cannot tell which provider kind the user picked. The companion no longer rejects them, `src/lib/desktop.js` drops them for subscription agents, and the page console gets a named warning through a `_warnings` field that `page-api.js` logs and strips, so the public result shape is unchanged.
- **Consent on a fresh install.** The new level 1/2 guard could not distinguish "status failed to load" from "no provider configured yet", so `requestAccess()` on a clean profile showed a disabled **Allow** plus a misleading message, contradicting the dialog's own accurate first-run notice. It now blocks only when `broker.status` actually failed, and the notice sits in the footer beside the button rather than at the bottom of the scroll.
- **Validation.** A site restating a capability its `level` already implies was rejected as a duplicate, though the duplicate came from the bundle expansion; uniqueness is now checked against what the site passed. `validateSiteToolResult` threw a raw `TypeError` on a non-array `content` instead of a protocol error.
- Two findings were left unfixed on purpose and are now written down under **Known v1.1 limitations** in [SECURITY.md](../SECURITY.md): the `ToolSession.flush()` batching race, whose real fix is serializing the MCP bridge, and the dashboard token's non-constant-time comparison.
- Removed the unreachable `arjunah-ui`/`snapshot` content-script handler — nothing in the repo sends that message. Added a `scripts/check.mjs` guard that fails on pre-1.0 page-API names in `sample-site/dist` and `demo`; verified it catches the `window.ai.site.register` breakage that shipped in 1.1.0-alpha.1.

## 2026-09-19 — naming, `window.ai.arjunah`, `enable()`

- The project, protocol, extension, and companion are **अर्जुनः** (romanized _Arjunah_; अर्जुनः कृष्णं पश्यति, "Arjuna sees Krishna": the extension sees both the AI and the human, so the website does not have to). Every user-visible title, label, and document says अर्जुनः; code, paths, and identifiers use the ASCII slug: npm package `arjunah`, bin `arjunah-desktop`, env prefix `ARJUNAH_*`, page events `arjunah:ready` / `arjunah:conflict`, widget host id `arjunah-extension`, bridge channel `arjunah-v0.1`, progress event `arjunah-progress`, bridged MCP server `arjunah` (`mcp__arjunah`), Firefox add-on id `arjunah@open-web.dev`, icon `src/icons/arjunah.svg`, types `types/arjunah.d.ts`, release archives `arjunah-<browser>-v<version>`.
- The page API lives at `window.ai.arjunah`. `window.ai` is a shared extensible namespace (created as a plain non-writable object when absent, reused when another actor already created one), so other extensions can coexist under their own keys; `arjunah:conflict` fires only when `window.ai.arjunah` exists or `window.ai` is not an extensible object. The root object is wallet-shaped: `isEnabled()` (a level 1 or 2 grant exists), `enable()` (defaults to level 1 and resolves to a **session** carrying `grant`, `permissions.query()`, `providers`, `models`, `context`), `disable()` (drops the origin's grant), plus the level 0 `site` and `chat` that need no grant. A page cannot reach `models`, `providers`, or `context` without a session; a session kept across `disable()` gets `PERMISSION_REQUIRED`.
- The companion's data directory is `arjunah` under the OS application-support folder (`ARJUNAH_DESKTOP_HOME` overrides it). This is the first public release, so the store carries no migration code.
- Documents now say _the extension_ (defined in SPEC section 1 as the browser extension) instead of the jargon term for it; SPEC section 1 introduces the three access levels before section 3 uses them. Code identifiers such as the internal error class and bridge method names are unchanged.

### Root cause and repair

- A minimal real OpenAI request using GPT-5.6 Sol reproduced HTTP 400. OpenAI explained that function tools with reasoning are unsupported on `/v1/chat/completions`, and specified either `/v1/responses` or `reasoning_effort: "none"` as the supported paths. The same request with `none` returned HTTP 200. The environment's Luna model independently reproduced the same restriction.
- The production adapter now sets `reasoning_effort: "none"` for GPT-5.6 tool requests and tool-result continuations. The selected model stays unchanged. Plain chat and other model families retain their existing behavior. This intentionally does not add Responses API support.
- Settings Test connection now verifies actual generation with a synthetic tool definition; failed, empty, or tool-only probe responses are not reported as success. It does not use page context, invoke site tools, or save settings. The selected model is preserved when loading model suggestions.
- The command-line live check now exercises the production adapter across a complete synthetic function-call/result round trip.
- Browser fixtures were stale: they attempted to save local endpoints despite production now allowing only OpenAI. Tests now stage a disposable extension copy that redirects only its provider transport to the local mock. Production source, endpoint enforcement, packaged artifacts, and the user's extension are not modified by the test transport.
