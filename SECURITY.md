# Security policy and threat model

## Reporting

Please report suspected vulnerabilities privately to [sudip@yama.com.np](mailto:sudip@yama.com.np) before publishing details. Include the extension version, browser version, proof of concept, and expected impact. This prototype has no hosted backend and no bounty program.

## Important properties

- API keys are stored in `chrome.storage.local`. This protects them from ordinary page JavaScript, not from a compromised browser profile, malicious extension with sufficient privileges, endpoint compromise, or local malware.
- Every privileged page call is authorized from the actual top-level runtime sender origin. Page-provided origin values are ignored. Hosted model/tool work is also bound to a document session and registration, with rechecks before later operations and after awaited results.
- Grant mutations are serialized. Revocation, navigation, registration replacement, unregister, and chat reset invalidate outstanding hosted work. Tools that already started may have irreversible page-side effects; cancellation prevents further calls and transmission of late results, and cannot undo those effects.
- Saved credentials are reused only for the same provider origin, including connection tests. Settings receives key-presence metadata; users can explicitly remove a key without deleting the endpoint/model.
- Consent and chat are rendered in a closed Shadow DOM owned by the content script. Page code can still obscure or imitate browser UI; users should confirm the extension branding and requested origin.
- Model output, page context, site prompts, site tool output, and MCP output are all untrusted. The extension's small Markdown renderer constructs allowed DOM elements itself and assigns all model-authored leaf content with `textContent`; it never injects model HTML.
- Sites see only the model catalog the user exposed to them: opaque provider and model identifiers, display names, and capability flags. Account identities, plan names, quotas, and local usage are shown only in extension-owned UI (popup, options, widget) and never cross the page bridge.
- Hosted chat (level 0) grants `chat.hosted`, not `models.generate`: the extension generates on the site's behalf and the page cannot call the model directly until it asks for level 1 or 2 and the user approves.
- Provider answer and reasoning deltas are private extension progress. They travel only from provider/companion to the background and the closed-shadow hosted widget, never through `window.ai.arjunah`; partial output is bounded, removed on cancellation, and discarded for rounds that resolve to tool calls. The final validated response is the only answer committed to chat history.
- Widget options (`widget.controls`) are site-authored labels and user-set values. Their disclosed values are appended to the conversation as one untrusted system line; they cannot change permissions, the model, or consent text, and they are part of the fingerprinted contract.
- Extension-collected tool inputs are separately declared and fingerprinted, prompted in extension-owned UI, validated as bounded scalar values, and bound to one active site-tool invocation. अर्जुनः does not add them to the model schema, model messages, or chat history. The page tool still receives each value and can exfiltrate it or echo it in its model-visible result, so the prompt identifies the receiving origin and tool and this mechanism must not be treated as protection from a malicious site.
- Image content parts are validated (allowed media types, base64 shape, count and size bounds) before any provider request and rejected outright for models without `vision`. Provider-returned images pass through only when they are validated data URLs of those types.
- The extension requires access to HTTP(S) pages so it can inject `window.ai.arjunah`. It does not read or transmit page context until the relevant origin grant and per-chat context toggle permit it.
- The desktop companion listens only on loopback, requires an explicit six-digit pairing per browser profile, stores only a hash of each pairing token, and rejects requests from web origins or non-loopback hosts. Browsers hold their pairing token in extension storage with the same protections as the API key.
- Desktop providers run locally installed agent CLIs with their built-in file, shell, web, and editing tools disabled, in an empty scratch directory, with a minimal environment and without the user's own MCP servers or project instructions. Only the site tools the user approved for the current turn are bridged to the agent, through a per-session MCP endpoint with its own random token, and the tools still execute inside the page.

## Known v0.4 limitations

- Codex has no supported way to remove its shell tool. On macOS the companion therefore wraps the whole Codex process in an additional seatbelt profile (`sandbox-exec`) that denies reads and writes of every top-level entry in the user's home directory except Codex's own data folder, denies listing the home directory itself, and allows only the run's scratch and temp folders; Codex's inner sandbox then cannot start, so model-issued shell commands fail instead of reading files, and the model is told it has no shell. Every command Codex attempts is streamed to the widget as an activity card. On platforms without `sandbox-exec` Codex keeps only its read-only sandbox, so a site assistant could ask it to read files; it stays disabled until the user enables it on the dashboard after reading the notice. Claude Code and OpenCode runs have no shell tool.
- The companion trusts other processes of the same operating-system user, as any local application does. The dashboard token protects only against web pages, and the synchronized OpenAI key is stored in a user-only file rather than the OS keychain.
- Configuration sync uses last-writer-wins revisions and includes the OpenAI API key so every paired browser can use it. Do not pair a browser profile you do not control.
- Pairing tokens do not expire; revoke them from the dashboard or the extension when a browser is retired.
- An optional T3 Code connection stores a T3 bearer token (T3's standard scopes) in the companion's 0600 data file, masked on the dashboard and never sent to browsers. अर्जुनः uses it only for read calls and the explicit provider refresh; it never starts T3 threads. Disconnect on the dashboard removes the token.
- Desktop providers keep one agent session per open hosted chat (a _thread_) so later turns do not replay the transcript. While a thread lives, the agent CLI persists that conversation in its own session store (`~/.codex/sessions`, `~/.claude/projects/<scratch-dir>`, OpenCode's session database) on this computer; the companion deletes Codex and Claude Code session files when the thread ends (page navigation, chat reset, 30 minutes idle, or app shutdown) and cannot delete OpenCode's. Threads are keyed by a random per-conversation id and are never shared across origins or tabs.
- The macOS outer sandbox for Codex denies each top-level entry of the home directory that exists when the run starts (except Codex's own data and the run's scratch folder). A folder created at the top level of the home directory during a run is not covered until the next run.

- Quota display depends on providers reporting one; none of the current adapters (OpenAI API key, Claude Code, Codex, OpenCode) exposes quota, so the UI says so and shows only the local request/token ledger.
- Desktop subscription providers do not accept image input today (`supportsVision` false); the widget hides the attach control and the extension rejects image parts for them before contacting the companion.
- Chrome local storage is not an OS keychain. Use a low-scope provider key and provider-side quotas.
- The single provider endpoint and permitted model are user configured; sending data to that provider is a user trust decision. Provider and MCP redirects are rejected, and ambient cookies are omitted.
- The Firefox package declares `authenticationInfo`, `personalCommunications`, `browsingActivity`, and `websiteContent` as required data categories because provider credentials, user chat, approved page URLs, and optional page snapshots can leave the browser for the user-selected provider. The extension's own per-origin and per-turn controls remain stricter than this installation-level declaration.
- Remote MCP authentication provisioning and OAuth are intentionally absent. A site cannot supply Authorization or Cookie headers.
- Tool calls are sequential and capped, but a permitted site tool retains all authority that the page already has.
- Hosted approval records include validated assistant-contract fingerprints, MCP origins, and discovered tool metadata fingerprints. Changes require redisclosure before another model request. Endpoint approval permits MCP discovery; an additional tool approval is required before model generation/invocation. Definitions and full prompts are inspectable in the consent dialog.
- A remote server can change its actual behavior without changing tool metadata. Metadata consent is not a guarantee of that server's implementation. The extension supports a documented bounded JSON Schema subset and rejects unsupported assertions; it does not claim full schema-dialect validation.
- Content scripts do not run on browser-internal pages, the extension store, or pages prohibited by enterprise policy.
- The implementation does not attempt to defeat a malicious page that visually spoofs an extension consent dialog. Browser-native permission prompts would be preferable in a future standardized API.
