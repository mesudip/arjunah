# Security policy and threat model

## Reporting

Please report suspected vulnerabilities privately to [sudip@yama.com.np](mailto:sudip@yama.com.np) before publishing details. Include the extension version, browser version, proof of concept, and expected impact. This prototype has no hosted backend and no bounty program.

## Important properties

- API keys are stored in `chrome.storage.local`. This protects them from ordinary page JavaScript, not from a compromised browser profile, malicious extension with sufficient privileges, endpoint compromise, or local malware.
- Every privileged page call is authorized from the actual top-level runtime sender origin. Page-provided origin values are ignored. Hosted model/tool work is also bound to a document session and registration, with rechecks before later operations and after awaited results.
- Grant mutations are serialized. Revocation, navigation, registration replacement, unregister, and chat reset invalidate outstanding hosted work. Tools that already started may have irreversible page-side effects; cancellation prevents further calls and transmission of late results, and cannot undo those effects.
- Saved credentials are reused only for the same provider origin, including connection tests. Settings receives key-presence metadata; users can explicitly remove a key without deleting the endpoint/model.
- Consent and chat are rendered in a closed Shadow DOM owned by the content script. Page code can still obscure or imitate browser UI; users should confirm the extension branding and requested origin.
- **The page can watch what you type in the panel.** The panel lives in the page's own document, and keyboard, input, and paste events leave a closed shadow root, so a page's listener on `window` sees every key typed there: chat messages, values typed into an extension-collected input prompt, and masked values too (a password field hides the value on screen, not the keystrokes). For a site tool's own inputs and a hosted external loop's this changes nothing, since the value goes to that site anyway. For a declared remote tool's input (SPEC 7.8), which the extension sends to the MCP server's origin, it means the page you are on can see it as well; the prompt says so ("<origin> can see what you type here"). Do not type a secret into the panel that the page itself must not learn. Moving that prompt into an extension-owned frame is future work.
- `enable()` needs no user gesture, so a page chooses when the consent sheet opens. The sheet focuses itself, never Allow, ignores synthetic clicks, and arms Allow only after it has been shown for one second without a break in a visible, focused tab; in Chrome it also stays disarmed while anything covers it or the page makes the extension's UI transparent (IntersectionObserver v2). A keystroke the visitor meant for the page, or a click on a decoy drawn over the sheet, therefore cannot approve it. Text the site wrote is shown as single lines with direction overrides and invisible characters removed, so it cannot reorder the sheet's sentences or draw lines that imitate them.
- Model output, page context, site prompts, site tool output, and MCP output are all untrusted. The extension's small Markdown renderer constructs allowed DOM elements itself and assigns all model-authored leaf content with `textContent`; it never injects model HTML.
- Sites see only the model catalog the user exposed to them: opaque provider and model identifiers, display names, capability flags, context windows, reasoning levels, `limits`, and the coarse `kind`, `local`, and `builtinTools` traits (SPEC 2, item 11); `local` never says where a model runs. Account identities, plan names, quotas, and local usage are shown only in extension-owned UI (popup, options, widget) and never cross the page bridge.
- Hosted chat (level 0) grants `chat.hosted`, not `models.generate`: the extension generates on the site's behalf and the page cannot call the model directly until it asks for level 1 or 2 and the user approves.
- Provider answer and reasoning deltas of anything the extension composes (hosted chat at level 0) are private extension progress, and so are the activity and stall notices of the rounds it answers for a hosted external loop; a loop round's deltas reach the loop only when its `model.client` asked with `stream: true`, as bounded `model-results` posts through the page's own `loop.fetch`. They travel only from provider/companion to the background and the closed-shadow hosted widget, never through `window.ai.arjunah`; partial output is bounded, removed on cancellation, and discarded for rounds that resolve to tool calls. The one stream a page receives is its own round's (`models.stream`, `conversation.stream`, SPEC 5.3 and 10): the answer and reasoning text of a request the page itself sent, coalesced to at most 4,000 characters per message within 250 ms, held to the result's own 120,000-character answer and 12,000-character reasoning bounds by the background, the content script, and the page API in turn, posted only under the page session and the request id the content script forwarded, and never carrying tool calls, agent commands or phases, usage, or provider state. Its result is the same validated result `models.generate` returns, and remains authoritative. A provider stream has no total size cap, but the parser holds one event at a time (at most 8,000,000 bytes) and keeps only bounded text and tool arguments, so a runaway or hostile stream cannot grow the service worker's memory. Streamed thinking is merged for at most 250 ms before one message reaches the widget, which keeps at most 60,000 characters of it per turn on screen. The final validated response is the only answer committed to chat history.
- Widget options (`widget.controls`) are site-authored labels and user-set values. Their disclosed values are appended to the conversation as one untrusted system line; they cannot change permissions, the model, or consent text, and they are part of the fingerprinted contract.
- Extension-collected tool inputs are separately declared and fingerprinted, prompted in extension-owned UI, validated as bounded scalar values, and bound to one active site-tool invocation. अर्जुनः does not add them to the model schema, model messages, or chat history. The page tool still receives each value and can exfiltrate it or echo it in its model-visible result, so the prompt identifies the receiving origin and tool and this mechanism must not be treated as protection from a malicious site.
- Transcript cards are site-authored UI drawn inside extension UI. A card is a bounded JSON tree (text, list, button, form) with no HTML, Markdown, links, images, or unknown node types, validated independently by the page API, the content bridge, and the background before anything is drawn, and every string is assigned with `textContent`. The model receives only the tool's text part, never the card. A card button either sends the exact declared text the user can see as an ordinary user turn, or fires a page callback that never becomes a model message or a tool argument. Declaring a card output is part of the fingerprinted contract and is disclosed in consent.
- Tool progress is presentation only. It is capped in length and count, replaced in place, discarded with the turn, and never enters model messages, chat history, or a stored transcript.
- A site that declares `threads` stores the conversation itself, so consent says so before the first turn. Messages it supplies back are untrusted model input: they are bounded and re-validated by the extension, rendered with a visible marker, placed in the provider request between explicit untrusted-history markers, and truncated to the extension's own budget after any truncation the site performed. A supplied transcript cannot widen the disclosed contract, and the extension never persists thread contents itself.
- An MCP server may declare its tools in the contract instead of being discovered. The declarations are fingerprinted like site tools, so the server is never asked what it offers and cannot widen its own tool set between consent and the call. Site-provided headers are page-authored and are never secret from the page.
- A hosted external loop (SPEC 15.1, `loop` in the manifest) runs the conversation outside the extension while the extension hosts the panel. The extension never contacts the site's server: every route goes through the page's `loop.fetch`, so it carries only what the page could already send, and the loop sees everything the visitor types and every reply, which consent says, with the composer's fixed wording and no system-prompt disclosure because there is none. Its grant is an ordinary level 1 or 2 grant bound to the contract fingerprint, so `model.client` rounds get exactly the validation, bounds, `require`, revocation, and usage ledger of a page's `models.generate`; only section 5.3 request fields cross, and conversation ids are minted and verified per origin. Page context sharing is off in this shape. Every stream event and route answer crosses the page bridge as bounded text (2,000,000 bytes per stream, 1,000,000 per JSON answer, counted again by the content script), only the listed event types are drawn, cards pass the section 7.4 validator, and `tool.client` arguments are checked against the declared schema in the background before the page handler runs. Running the site's tools for a loop needs `tools.site` in the grant, which the loop's consent requests and lists, and is refused without it. A loop's approval and input prompts appear inside the extension's own panel, so consent says the loop can ask for approvals and, only when the manifest declares `loop.inputs: true`, for values (an undeclared `input.client` is cancelled without a prompt); each prompt names the site's origin as the one asking, and a site-written tool name that contains the extension's name is not shown. A panel line names the composer for as long as the loop drives it.
- The site's own models (SPEC 15.2) answer with no visitor credential and no ledger entry, so the visitor's provider is never contacted for them; consent says the visitor's AI is not used. The site's `generate` runs in the page and receives the conversation the extension composed (messages, tool results, any page context the visitor chose to share), which the page could already read. Its result is validated like a provider's: shape, the answer and reasoning bounds, images, usage as non-negative integers, and tool calls only to tools that round offered, failing the round as `PROVIDER_ERROR` otherwise. The panel shows only metadata the site declared and never estimates context, effort, or usage. The visitor's choice of a site model is stored on the grant as an id the contract must still declare.
- `requiresApproval` (SPEC 7.8) makes the extension ask in its own panel before each call of a declared site or remote tool, after schema validation and with the model's arguments shown as text. Only an explicit Approve runs the tool; a denial, the two-minute timeout, cancellation, navigation, or revocation answers the model with a tool error. A declared remote tool's `userInputs` are collected in the panel, labelled with the server's origin, validated, and sent only in that call's `params._meta.arjunah.inputs`; the values never enter arguments, model messages, history, activity events, or logs. As with site-tool inputs, the receiving server can misuse what it is given.
- The standalone `arjunah-widget` package shares this renderer but provides none of these wallet guarantees: the site's loop (its backend, or page code behind `backend.fetch`) owns inference, tools, and conversations and sees everything the visitor types. It carries no consent UI and no provider credential, and never defines or replaces `window.ai.arjunah`, and its README states this plainly. In bridged mode (SPEC 14.7) it calls `window.ai.arjunah` exactly as any page may, holding an ordinary level 1 or 2 session: that restores credential non-disclosure, exact-origin revocable grants, and the visitor's choice of model, and nothing else, because the site's loop still writes every prompt and the extension cannot show them.
- Image content parts are validated (allowed media types, base64 shape, count and size bounds) before any provider request and rejected outright for models without `vision`. Provider-returned images pass through only when they are validated data URLs of those types.
- Images sent to a desktop provider are bounded again in the companion (allowed media types, base64 shape, four per message, eight per prompt, 2,000,000 base64 characters each), refused on any message whose role is not `user`, and dropped for a provider that does not advertise vision. Where an adapter needs a file on disk it writes one only into the run's scratch directory, which the outer sandbox already permits, and that directory is removed with the run.
- The diagnostic logs of the extension and the companion are bounded metadata: stage names, provider and model ids, counts, durations, error codes, and the agent CLI's stderr and exit status. Prompts, model output, tool arguments and results, page context, API keys, pairing codes, and bearer tokens are not written to them, and a logged command line keeps its flags while eliding every value over 60 characters. The companion's log is served over the paired loopback connection only, the extension's never leaves the browser profile, neither is part of configuration sync, and each can be cleared from the settings page. A logged CLI error line is still the CLI's own text and may name paths on the computer, so treat a shared log as it would any local diagnostic output.
- The extension requires access to HTTP(S) pages so it can inject `window.ai.arjunah`. It does not read or transmit page context until the relevant origin grant and per-chat context toggle permit it.
- The desktop companion listens only on loopback, requires an explicit six-digit pairing per browser profile, stores only a hash of each pairing token, and rejects requests from web origins or non-loopback hosts. Browsers hold their pairing token in extension storage with the same protections as the API key.
- Desktop live updates use an authenticated loopback WebSocket. The pairing or dashboard token is carried only in the WebSocket subprotocol (never the URL or event body), and events contain only a monotonic revision and a coarse topic. Reconnects and events cause an authenticated state fetch, so the stream does not become a second source of credential, account, grant, or provider data.
- Desktop providers run locally installed agent CLIs with their built-in file, shell, web, and editing tools disabled, in an empty scratch directory, with a minimal environment and without the user's own MCP servers or project instructions. Only the site tools the user approved for the current turn are bridged to the agent, through a per-session MCP endpoint with its own random token, and the tools still execute inside the page.

## Known v1 limitations

- Codex has no supported way to remove its shell tool. On macOS the companion therefore wraps the whole Codex app-server process in an additional seatbelt profile (`sandbox-exec`) that denies reads and writes of every top-level entry in the user's home directory, denies listing the home directory itself, and allows only the run's scratch and temp folders. The app-server gets an isolated `CODEX_HOME` under that scratch directory containing a mode-0600 copy of `auth.json`, so it loads neither the user's config, rules, personal MCP servers, nor unrelated sessions. Codex's inner read-only sandbox then cannot use shell commands to read user files, and the model is told it has no shell. Every command Codex attempts is shown in the widget's activity. On platforms without `sandbox-exec` Codex keeps only its read-only sandbox, so a site assistant could ask it to read files; it stays disabled until the user enables it on the dashboard after reading the notice. Claude Code and OpenCode runs have no shell tool.
- The companion trusts other processes of the same operating-system user, as any local application does. The dashboard token protects only against web pages, and synchronized OpenAI, OpenCode Zen, and Ollama keys are stored in a user-only file rather than the OS keychain.
- Configuration sync uses last-writer-wins revisions and includes OpenAI, OpenCode Zen, and Ollama API keys and the self-hosted Ollama address, so every paired browser can use them. Keys are masked in the desktop dashboard. A synced Ollama address goes through the same address checks as a typed one, and model catalogs are never synced: each browser reads capabilities from the server itself. Do not pair a browser profile you do not control.
- Pairing tokens do not expire; revoke them from the dashboard or the extension when a browser is retired.
- An optional T3 Code connection stores a T3 bearer token (T3's standard scopes) in the companion's 0600 data file, masked on the dashboard and never sent to browsers. अर्जुनः uses it only for read calls and the explicit provider refresh; it never starts T3 threads. Disconnect on the dashboard removes the token.
- Desktop providers keep one agent session (a _thread_) per open hosted chat and per page conversation (SPEC 5.4) so later turns do not replay the transcript. While a thread lives, the agent CLI persists that conversation locally (Codex inside the thread's isolated scratch `CODEX_HOME`, Claude Code under `~/.claude/projects/<scratch-dir>`, OpenCode in its session database). The companion removes it when the thread ends (page navigation or chat reset for hosted chat; `conversation.release()`, `disable()`, or revoking the site for a page conversation; 10 minutes idle; or app shutdown): Codex disappears with the scratch directory, Claude Code's session files are deleted directly, and OpenCode's is removed through its own `session delete` command. A hosted thread's id is derived the same way from the origin and the panel's random per-conversation id, and is recorded with its origin, so revoking the site and clearing stored conversation state end it too, and after a clear the panel never resumes the old session. The companion runs the turns of one thread one at a time, so two requests on the same conversation never share an agent session or its scratch directory, and ending a thread stops its running agent before deleting the thread's data. A page conversation's thread id is an HMAC of the origin and the extension-minted conversation id under the per-install key, so threads are never shared across origins and a page cannot name another origin's; documents of the same origin that open the same conversation id do share its thread, as they share its provider state. A plain `models.generate` uses no thread.
- The companion surfaces each of the agent's tool calls to the browser as the agent issues it, and sibling calls stay pending and resume independently as their results return. A pending call that the browser never answers ends the session after two minutes, killing that agent run: the turn loses its progress rather than producing a wrong answer, and no tool result crosses conversations, because call ids are 12 random bytes.
- The macOS outer sandbox for Codex denies each top-level entry of the home directory that exists when the run starts. A folder created at the top level of the home directory during a run is not covered until the next run.

- Quota display depends on providers reporting it. Claude Code and Codex expose quota when their local interfaces provide it; OpenAI API keys, OpenCode, and Ollama currently show only the local request/token ledger.
- The OpenCode **desktop CLI** accepts no image input. `opencode run` offers no way to deliver one, so models reached through that subscription provider report `supportsVision` false. This does not apply to the OpenCode Zen API-key provider, which sends images through each model family's native HTTP format. Claude Code and Codex desktop providers also accept images.
- A self-hosted Ollama server is reached at the address the user typed, over `http` only when that address is loopback, private (RFC 1918, CGNAT/Tailscale, link-local, IPv6 ULA/link-local), or a local-by-construction name (`.local`, `.lan`, `.home.arpa`, `.internal`, a single label); anything else must be `https`. Names are not resolved, so a local-looking name that resolves to a public address is the user's own choice. The address, like any account detail, never reaches a page: the page sees the provider kind `self-hosted` and its model ids.
- Ollama refuses requests whose `Origin` it does not allow, and a browser extension's origin is never on its default list. The extension therefore installs one dynamic `declarativeNetRequest` rule that removes `Origin` from requests to the configured server's origin, conditioned on the extension itself as the initiator, so a web page's requests to the same server keep the `Origin` that Ollama's check inspects. A second rule with the same scope exists only while an unsaved address is being tested or saved. Browsers without the API keep the header and receive a refusal that explains `OLLAMA_ORIGINS`. Only a 403 with an empty body, which is how Ollama's own Origin and Host checks answer, is reported that way; a 403 that says something (an authenticating proxy, a firewall page) is reported as the server refusing the request, and as a rejected key when one is set.
- A self-hosted Ollama server can list cloud models it forwards to ollama.com (`ollama pull …-cloud`). Discovery marks them from the server's `remote_host`/`remote_model` metadata or the `-cloud` name and settings label them as running on ollama.com, but they remain under the self-hosted provider: choosing one sends the conversation to Ollama's hosted service through the user's server.
- Ollama error text from a generation is read only to choose one of the extension's own sentences (model missing, no image support, out of memory, and so on); it is never shown, since a server's prose can quote the prompt. The one exception is a model the server cannot describe: settings (an extension page, never a site) show the server's own error and version for it, because no guessed cause can be trusted there. That text comes only from `/api/show`, whose request carries nothing but a model name, and is unwrapped, stripped of control characters, and capped at 200 characters.
- Chrome local storage is not an OS keychain. Use a low-scope provider key and provider-side quotas.
- The single provider endpoint and permitted model are user configured; sending data to that provider is a user trust decision. Provider and MCP redirects are rejected, and ambient cookies are omitted.
- The Firefox package declares `authenticationInfo`, `personalCommunications`, `browsingActivity`, and `websiteContent` as required data categories because provider credentials, user chat, approved page URLs, and optional page snapshots can leave the browser for the user-selected provider. The extension's own per-origin and per-turn controls remain stricter than this installation-level declaration.
- The chat renderer trusts cards already validated by the page API, content bridge, and background broker instead of re-validating each card tree itself before drawing it. A card stored by a site-owned thread is re-validated by the content bridge before the renderer sees it, and the model-visible history is independently re-validated by the broker.
- Card-id uniqueness is enforced within each live turn: the broker refuses a second card that reuses an id the turn already claimed. Ids from site-stored history are not part of that set, so a stored card re-validated on load can share an id with a new live card, and a local card action (which addresses cards by id) may then swap or rewrite the wrong card in the renderer. Stored cards are still shape-validated before drawing and never reach the model, so this is a display-addressing concern rather than a model-injection path.
- Remote MCP authentication provisioning and OAuth are intentionally absent. A site cannot supply Authorization or Cookie headers.
- Tool calls are sequential and capped, but a permitted site tool retains all authority that the page already has.
- Hosted approval records include validated assistant-contract fingerprints, MCP origins, and discovered tool metadata fingerprints. Changes require redisclosure before another model request. Endpoint approval permits MCP discovery; an additional tool approval is required before model generation/invocation. Definitions and full prompts are inspectable in the consent dialog.
- A remote server can change its actual behavior without changing tool metadata. Metadata consent is not a guarantee of that server's implementation. The extension supports a documented bounded JSON Schema subset and rejects unsupported assertions; it does not claim full schema-dialect validation.
- Content scripts do not run on browser-internal pages, the extension store, or pages prohibited by enterprise policy.
- The implementation does not attempt to defeat a malicious page that visually spoofs an extension consent dialog. Browser-native permission prompts would be preferable in a future standardized API.
